# lingtai.mcp_servers

Curated and built-in MCP server package implementations shipped inside the `lingtai` Python distribution. They are launched by catalog/script entry points such as `python -m lingtai.mcp_servers.<name>` and expose real addon tools (IMAP, Telegram, Feishu, WeChat, WhatsApp, Cloud Mail), daemon lifecycle tools, plus bundled progressive-disclosure manuals.

## Components

| File / folder | Role |
|---|---|
| `_skill.py` | Shared bundled-skill helper: re-exports the kernel-owned `split_frontmatter` from `lingtai.kernel._frontmatter` (one impl shared with the prompt-section catalog; kernel never imports the wrapper), `load_skill()` loads package `SKILL.md`, `manual_action_description()` injects frontmatter into the schema, and `manual_payload()` returns the manual body + absolute path without sidecar lists (`_skill.py:36-79`). |
| `_identity.py` | Shared public-identity envelope/path/write helper for curated messaging MCPs: builds the `lingtai.mcp.identity.v1` document, computes `system/mcp_identities/<name>.json`, and performs the newline-terminated atomic JSON write. Provider-specific account fields and redaction stay in each provider. |
| `_results.py` | Shared typed-result builders for the SDK v2 low-level server, which no longer wraps handler return values: `json_tool_result()` builds the canonical `CallToolResult` (JSON text block + `structured_content`, with `is_error` tracking the provider payload's `status`), and `text_resource_result()` builds the single-text-block `ReadResourceResult`. One implementation instead of seven. |
| `daemon_common/` | Built-in daemon lifecycle MCP. `daemon_common/server.py:1-151` exposes `finish(status, summary?, reason?, artifacts?)`, validates the call, and atomically writes the internal per-run `daemon_completion.json` file named by `LINGTAI_DAEMON_COMPLETION_FILE`; daemon runners validate that file before allowing success. |
| `telegram/`, `imap/`, `feishu/`, `wechat/`, `whatsapp/`, `cloud_mail/` | Curated messaging MCPs. TelegramManager requires an injected `NotificationStorePort`; `telegram/server.py` constructs one POSIX adapter, and handled-mirror policy runs against the current payload in one compare-update so newer mirrors survive (`src/lingtai/mcp_servers/telegram/manager.py:415-425`, `src/lingtai/mcp_servers/telegram/manager.py:1239-1281`, `src/lingtai/mcp_servers/telegram/server.py:655-663`). The external LICC path/envelope and persistent-message lanes remain unchanged. `whatsapp/_family.py` mirrors `telegram/_family.py`'s native LTP-v2 tool family: one strict root envelope (`action`/`input`/`reasoning`/`summarize`) with an action-correlated `input` branch per action, dispatched through `handle_whatsapp()`; `manager.py`'s `SCHEMA`/`ACTIONS` now alias `_family.py`'s, and the manager stays the internal flat action/business boundary behind it. |
| `telegram/task_card/` | Telegram-owned **resident + programmable projection** unit (governed component with paired `ANATOMY.md`/`CONTRACT.md` + packaged docs). `TaskCardResident` owns shared channel frames, route locks, compose, enablement, and `ensure`/`project`; `TelegramManager` remains its Telegram render/transport/persistence adapter. The public `task_card` tool has moved to `src/lingtai/tools/task_card/`; Telegram now reads the intrinsic artifact and projects it read-only. See `src/lingtai/mcp_servers/telegram/task_card/ANATOMY.md` and `src/lingtai/tools/task_card/ANATOMY.md`. |
| Per-package `SKILL.md` | The human/agent-facing bundled manual. If a manual has sidecars, the sidecar inventory and relative paths live in this markdown, not in the tool payload. |
| `pyproject.toml` package-data entries | Ships every curated MCP `SKILL.md`; `reference/**/*` and `assets/**/*` are also packaged for future sidecar files (`pyproject.toml:81-86`). |

## Connections

- Catalog/script launchers (`pyproject.toml:43-49`) start these servers as subprocess MCPs; agents activate them through the generic MCP capability (`src/lingtai/tools/mcp/ANATOMY.md`).
- Manager schemas include `manual` in each action enum and use `_skill.manual_action_description()` to advertise the bundled skill without loading the full body into the resident schema.
- Tests pin the manual contract, package-data sidecar support, and Telegram parity in `tests/test_mcp_skill_manuals.py` and `tests/test_telegram_rich_formatting.py`.
- `telegram/_family.py` and `imap/_family.py` each own an independent strict LTP-v2 envelope (`{action, input, reasoning, summarize?}`) built on `lingtai.tools.tool_family.ToolFamily`, with a dependency-free `_basic_validate` dispatch-safety gate that rejects an unknown action, non-string `reasoning`, unknown root field, or cross-branch `input` key before any manager I/O runs. Each manager module keeps its original flat `SCHEMA`/`DESCRIPTION` for the pre-migration per-action description text and `manager.handle()`'s legacy flat-args dispatch, then reassigns the module-level `SCHEMA` name to the family's composed schema (`SCHEMA = _family.TELEGRAM_SCHEMA` / `SCHEMA = _family.IMAP_SCHEMA`) so callers see the strict envelope while the manager's own internal dispatch boundary is unchanged. `tests/test_imap_toolfamily_ltpv2.py` is IMAP's family-specific evidence, mirroring `tests/test_telegram_toolfamily_ltpv2.py`.

## Composition

Parent: `src/lingtai/` wrapper package (`src/lingtai/ANATOMY.md`). Sibling wrapper areas include `agent.py`, `core/`, `services/`, and `intrinsic_skills/`. Curated MCPs are independent subprocess packages, not intrinsic capabilities.

## State

The package itself is mostly code + packaged manuals. Runtime state is per-agent and server-specific: e.g. message caches, contacts, inbox replay guards, credential-derived identities, or daemon completion sentinels live under the agent workdir/run dir or `.secrets/`, not in `src/lingtai/mcp_servers/`. The shared manual and identity helpers have no persistent state of their own. Telegram's per-account non-secret `state.json` (under `<workdir>/telegram/<alias>/`) additionally persists the resident Task Card id per chat under a `task_cards` map (`{chat_id: compound_id}`), loaded backward-compatibly and normalized against malformed values by `TelegramAccount._normalize_task_cards`, so the one tracked resident target per account+chat survives a refresh; it is not proof that historical unknown orphan cards do not exist. The same account additionally owns an **ephemeral, non-persisted** per-chat high-water mark of the latest observed Telegram message id (`_last_message_ids`, `telegram/account.py:190`), bumped by every inbound plain message the poll loop sees (`_process_update`) and every outbound `send_message`/`send_photo`/`send_document`, but never by an edit or delete; `_note_chat_message_id`/`get_last_message_id` (`telegram/account.py:1208,1235`) record and expose it, guarded by the same `_state_lock` as `task_cards`. Because Telegram message ids are monotonic per chat this mark is "the chat's last message id"; the manager reads it to keep the resident Task Card residing as the last message (Jason #5272/#5273/#5275). It is deliberately not persisted, so a refresh reports `None` (unknown) until the next observed message, and the manager treats an unknown latest-message mark conservatively by editing in place; malformed or cross-bound resident ids fail loud before transport, and neither condition authorizes deletion. Separately, `TelegramService` owns one current-agent delivery boolean in `<workdir>/telegram/taskcard.json`, loaded with a compatibility default of `True` and written through the kernel atomic JSON primitive with fsync; bound getter/setter callbacks let every configured account's local `/taskcard` command share that one value (`telegram/service.py`, `telegram/account.py`).

## Notes

- **Official SDK v2 handler shape (`mcp>=2,<3`, protocol `2026-07-28`).** Every bundled server is a low-level `Server` whose handlers are **constructor parameters** (`on_list_tools`, `on_call_tool`, `on_list_resources`, `on_read_resource`) — the v1 decorators are gone. Each handler is `async (ctx, params) -> <full typed result>`: `params.name`/`params.arguments`/`params.uri` in, `ListToolsResult`/`CallToolResult`/`ListResourcesResult`/`ReadResourceResult` out, built by hand because v2 wraps nothing. Attributes are snake_case (`input_schema`, `mime_type`, `is_error`, `structured_content`). Advertised capabilities are derived from which handlers were registered, so a tool-only server (`cloud_mail`, `daemon_common`) correctly claims no `resources`; none of these servers registers prompts, completion, subscriptions, or multi-round-trip, which is the intended product surface. A provider/domain failure remains a model-readable `CallToolResult(is_error=True)`; an unknown tool name or unknown resource URI is instead a lookup failure, which the 2026-07-28 schema classifies as `InvalidParamsError` — every curated handler raises an official `MCPError` with `code=INVALID_PARAMS` (`-32602`) and `data={"requested": name}` / `data={"uri": uri}` via the shared raisers in `_results.py`. Contract and tests: `src/lingtai/intrinsic_skills/lingtai-kernel-anatomy/reference/mcp-protocol.md`, `tests/test_mcp_sdk_v2_contract.py`.
- **Notification contract:** curated messaging MCPs that change structured notification metadata (`recent_messages`, `latest_incoming`, `referenced_messages`, stable IDs, routing hooks, or preview/body placement) must check `src/lingtai/services/LICC_NOTIFICATION_CONTRACT.md` in the same change.
- **Manual sidecar minimal contract:** `action="manual"` returns the main `SKILL.md` body, parsed metadata, and the main `SKILL.md` absolute `path` only. Concrete `assets/` and `reference/` lists MUST NOT be returned as structured tool fields; `SKILL.md` is the single source of truth for what sidecars exist and how to follow their relative paths.
- **Packaging discipline:** when adding manual sidecars, put their relative paths in `SKILL.md` and keep the package-data globs for `reference/**/*` / `assets/**/*` so wheels contain them (`pyproject.toml:81-86`).
- **Feishu strict LTP-v2 family:** `feishu/_family.py` owns the public envelope, mirroring `telegram/_family.py`'s split — `feishu_schema()` composes the closed root `{action, input, reasoning, summarize?}` (`action`, `input`, `reasoning` required) with one closed action-owned `input` branch per action (`send`, `check`, `read`, `reply`, `search`, `delete`, `edit`, `contacts`, `add_contact`, `remove_contact`, `accounts`, `manual`), and `handle_feishu()` is the always-authoritative dispatch gate: it rejects an unsupported root field, unknown/missing `action`, a non-object `input`, a non-string `reasoning`, a non-boolean `summarize`, and any cross-branch `input` key before any `FeishuManager` I/O. `FeishuManager.handle()` stays the internal flat action boundary and now also accepts the LTP-v2 shape directly (detected via `{"input", "reasoning"}.issubset(args)`), re-entering through `_family.handle_feishu` so both call shapes produce identical results; `manager.py`'s own flat `SCHEMA` literal was retired in favor of `SCHEMA = _family.FEISHU_SCHEMA`. `FeishuManager._manual()`'s existing flat `manual_payload()` result is unchanged and is what the family's `manual` child returns verbatim (no double wrap), matching `manual_action_description()`'s catalog line already embedded in the schema's `action` description. Contract and tests: `../tools/tool_family/CONTRACT.md`, `tests/test_feishu_toolfamily_ltpv2.py`, `tests/test_mcp_skill_manuals.py`, `tests/test_mcp_sdk_v2_contract.py`.
- **Feishu rich text/post outbound + thread-following reply:** the `send`, `reply`, and `edit` children require exactly one of the legacy plain `text` shortcut or a strict tagged `content` value (`text`, `markdown`, or raw `post` AST). Manager normalization maps that public union to the channel SDK outbound facade; the SDK converter owns Markdown-to-post conversion and safe long-message chunking, while account config keeps `max_attempts=1`. Send/reply results return the primary compound id plus ordered compound chunk ids, and one durable logical sent record retains the exact normalized content and physical chunk projection. `reply` reads the persisted target and defaults `reply_in_thread` from its `thread_id`; explicit booleans override, every chunk of a topic reply stays in-topic, and `reply_target_gone="fail"` forbids a silent fresh-send fallback. `edit` uses the SDK text/post edit path and refreshes the exact persisted sent record only after transport success. Public behavior and examples live in `feishu/SKILL.md`; focused coverage lives in `tests/test_feishu_rich_outbound.py`.
- **Feishu media/share/sticker outbound:** `send` and `reply` extend the same strict content union with `image`, `file`, `audio`, `video`, `share_chat`, `share_user`, and `sticker`; `edit` deliberately remains the SDK-supported text/post subset. Media sources are explicit absolute local paths or pre-uploaded provider keys — URLs and relative paths never enter the uploader — and manager normalization maps them to the SDK's upload/reuse shapes. Image/video may carry Markdown captions (wire `post`); file/audio captions remain unsupported. The account's narrow `_SingleAttemptOutboundAdapter` reuses SDK 1.x materialization/upload/chunking but calls `_create`/`_reply` exactly once per chunk, bypassing the SDK's otherwise-unconditional post-to-plaintext downgrade; reply-target and format failures therefore remain failures. Durable sent records retain the exact source descriptor for producer `read`, while their bounded LICC media summary contains only type/filename/size, never local paths or provider keys. Focused coverage lives in `tests/test_feishu_rich_outbound_media.py`.
- **Telegram public tool surface:** `telegram/server.py` now advertises exactly one public family in stable order: `telegram`. The public programmable Task Card family moved out of MCP ownership and into the intrinsic tools layer. Under official SDK v2 the low-level `Server` still validates only the typed MCP request envelope, not the advertised per-tool `input_schema`, so the handler remains the gate for per-tool argument semantics on the public `telegram` family.
- **Automatic Task Card: mechanical `logs/events.jsonl` broadcast, manager-owned (Telegram 8266-8295).** The automatic slot is a bounded, mechanical broadcast of the agent's own behavior, not a per-chat/per-route view or a BaseAgent-owned lifecycle model. `TelegramManager` owns one tail worker per manager instance (`_start_task_card_tail`/`_stop_task_card_tail`, `telegram/manager.py`), started/stopped exactly once by `TelegramManager.start()`/`stop()` — `telegram/server.py`'s `serve()` calls these instead of reaching into `manager._service.start()`/`stop()` directly, so the poll threads and the tail worker join one lifecycle. There is **no durable cursor/checkpoint file**: `_init_event_tail` reverse-tails `logs/events.jsonl` in bounded, growing chunks from EOF (`_reverse_tail_latest_rows`) to rehydrate the latest `_TASK_CARD_EVENT_WINDOW` (10) API-call groups and set the forward byte offset to EOF (or to the start of an unterminated final line, so a writer's in-progress row is re-read whole once complete rather than dropped) — on startup, refresh/molt, and after any detected truncation/replacement (smaller size or changed inode) — so `events.jsonl` remains the only durable behavior source. Every later poll (`_poll_event_tail`, 1s interval) seeks from the in-memory offset and reads only newly appended complete lines (`_append_new_lines`). For each complete line, the resident projection recognizes canonical public `diary`/text events and exact `tool_call` events; public text is redacted/capped, while a matching tool row's only extracted fields are `tool_name`, `tool_args.action`, and a redacted/capped `tool_args._reasoning`. On each window change, `_broadcast_task_card_event_window` renders once and projects that identical text to every persisted resident Task Card target through the `automatic` channel. The programmable channel is now separate: Telegram reads the intrinsic `taskcard/` artifact and projects it read-only. See `tests/test_telegram_task_card_event_tail.py`, `tests/test_telegram_task_card_programmable.py`, and `src/lingtai/kernel/base_agent/ANATOMY.md`.
- **Tracked resident Task Card target, composed per account+chat and kept at the last message (Jason #6665/#6667, #6894/#6899, #5272/#5273/#5275).** `_handle_task_card_update` (`telegram/manager.py:1717`) dispatches create/update/finalize through `_deliver_channel_frame` (`telegram/manager.py:1576`), which takes one stable per-account+chat transaction lock across automatic and programmable callers, re-reads the tracked resident inside that transaction, and commits composed channel state only after transport success. The durable `task_cards` map names one exact bot-owned resident target; it is not a scan or proof of global chat-history cardinality, and unknown historical orphan cards are never guessed at or deleted. If the resident is already the account's latest observed message, the manager edits it in place; an unknown high-water (`_resident_superseded`, `telegram/manager.py:1874`) remains conservative and never authorizes deletion. If a newer message deterministically supersedes it, `_rotate_task_card_to_latest` (`telegram/manager.py:1896`) uses the last committed render for a same-content edit/no-op existence probe on that exact resident id when available; after a cold in-memory start, the exact delete outcome itself is the existence/removal probe (`_replace_task_card_after_probe`/`_delete_task_card_message_outcome`, `telegram/manager.py:1820,1943`). Unknown/transient edit-probe errors fail closed. The exact old id must then be confirmed deleted, or Telegram must explicitly report it already missing, before any replacement send; unknown or permission delete failure surfaces `stale_delete_failed` and blocks the send (never a successful partial). This old-first ordering prevents tracked rotation from intentionally displaying two cards, while a replacement-send failure after confirmed deletion may leave zero and reports `old_resident_deleted`. A new resident write failure retains the sole new in-process id and surfaces successful-partial `resident_persist_failed`. Provider-confirmed edit-impossible recovery (`_recover_task_card_by_replacement`, `telegram/manager.py:1804`) follows the same delete/missing-confirm-before-send rule. Identical edit content is a successful no-op. Finalize uses the same transaction after the durable final reply pushes the card off the bottom; legacy scalar finalize keeps its historical done form. The per-chat last-message high-water mark is an ephemeral, int-only observation owned by `TelegramAccount` (`_note_chat_message_id`/`get_last_message_id`, `telegram/account.py`; rejects `bool`/non-`int`, not persisted, `None`-conservative after refresh).
- **Task Card render: rows, heartbeat elapsed, dynamic footer, bounded metadata, render-time "Last Updated" line.** `_format_task_card_text` (`telegram/manager.py:2740`) renders the batched multi-row form via `_format_rows_task_card_text` (`telegram/manager.py:2864`): one line per tool call (`tool.action`, redacted reasoning, own whole-second elapsed via `_format_elapsed` at `telegram/manager.py:3051`, `✓` when done) with **its own** inline `started_at` suffix — each row shows the exact captured instant for *that* row, never the first row's or any other row's. Malformed/missing `started_at` degrades to no inline suffix rather than raising. The card's final standalone line is always present (unlike the retired started_at-derived line, it never depends on any row carrying a stamp): `Last Updated: HH:MM:SS UTC±HH` (`_TASK_CARD_TIME_PREFIX`, `telegram/manager.py:111`), sourced from the **render instant** via `_task_card_render_time`/`_format_task_card_current_time` (`telegram/manager.py:2983`, `:123`) — never any row's start instant — and injectable via the `now` keyword for deterministic tests; its exact text is counted in the reasoning-excerpt budget. This label means when the automatic channel's event-tail snapshot was last rendered/updated — it is not a wall clock that must change on an unrelated programmable-channel edit. Redaction runs on each row before any excerpt/trim, and every row always stays represented (rows are never dropped; only per-row reasoning excerpts shrink). The `_TASK_CARD_TEXT_LIMIT` (3500) budget bounds that reasoning-excerpt shrinkage only, **not** the whole render: fixed per-row scaffolding is unbounded in row count, so many selected rows can push the render above the budget (and above Telegram's transport limit); the durable `/taskcard N` control bounds latest API-call groups to 1-10, while fixed scaffolding is not truncated. Both running and frozen renders carry `_TASK_CARD_FOOTER` (`telegram/manager.py:97`) plus a live `current: X` suffix built by `_task_card_footer` (`telegram/manager.py:114`) from the `normal_rows` keyword — the manager's three call sites (`_task_card_create`/`_task_card_update`/`_task_card_finalize`) pass `self._taskcard_normal_rows()`, which reads `TelegramService.taskcard_normal_rows()` (validated `1-10`, defaulting to `1` for narrow test/third-party service doubles that omit the getter) — so the footer always names the actual current operator setting, e.g. `/taskcard N sets normal rows (1-10, current: 3).`; immediately after it, `_format_task_card_metadata` (`telegram/manager.py:2811`) renders at most two lines / 150 characters from numeric session cache rate, cumulative cache miss/budget, API calls, and context usage, before the final `Last Updated` line. `TelegramManager` owns this render for the automatic channel; its rows come from the event-tail broadcast above (no `started_at`/elapsed/`done` fields — those keys, when present, originate only from the retired BaseAgent batch model's row shape and are simply not populated by the tailer). BaseAgent no longer builds rows, runs a heartbeat, or calls into this render at all — see the event-tail note above and `src/lingtai/kernel/base_agent/ANATOMY.md`.
- **Resident card, two fully independent composed slots — `automatic` + `programmable` (Jason #7258/#7259).** The one tracked resident target per account+chat is composed from two independent slots kept in `_task_card_channels` (`telegram/manager.py:506`, keyed `"{account}:{chat_id}"`). `_handle_task_card_update` (`telegram/manager.py:2377`) still owns the automatic create/update/finalize dispatch and retained legacy programmable-channel cleanup; current public programmable content does **not** originate from a Telegram-owned controller. Instead, `lingtai.tools.task_card` writes `<workdir>/taskcard/status` and `<workdir>/taskcard/taskcard.md`, and Telegram's programmable poller reads that intrinsic artifact read-only. Exact `active` plus a nonempty body is projected through `_broadcast_programmable_task_card_file` / `_deliver_channel_frame`; missing, invalid, inactive, blank, or unchanged producer state is a no-op that preserves the last committed Telegram resident state. Each channel follows only its own update path: automatic updates never read or touch the programmable producer artifact, and programmable projection never reads, polls, advances, or overrides the automatic event-tail/session state. With both slots present the programmable block is appended under a `— WATCH —` header. The retained `src/lingtai/mcp_servers/telegram/task_card/` controller/interface files remain shipped only as historical compatibility/projection documentation; the authoritative model-facing owner is `src/lingtai/tools/task_card/` (see its paired `ANATOMY.md`/`CONTRACT.md` and manual).
