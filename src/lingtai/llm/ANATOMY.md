# src/lingtai/llm/

LLM adapter layer — the four built-in provider families (`openai`, `anthropic`, `codex`, `claude-code`) with adapter registry, base classes, rate limiting, and interface converters. Other vendors are reached by pointing `openai`/`anthropic` at a compatible `base_url` (or an external pool such as sub2api/subs-pool); there are no per-vendor adapters. The operator-facing reference is the `llm-adapters` system-manual page (`src/lingtai/intrinsic_skills/system-manual/reference/llm-adapters/SKILL.md`).

> **Maintenance:** see the `lingtai-kernel-anatomy` skill. **Coding agents** update this file in the same commit as code changes. **LingTai agents** report drift as issues.

## Connections

- **Kernel types** — `__init__.py:3` imports `ChatSession`, `LLMResponse`, `ToolCall`, `FunctionSchema` from `lingtai.kernel.llm.base`; `ChatInterface` from `lingtai.kernel.llm.interface`.
- **ABC chain** — `LLMAdapter` (`base.py:114`) → abstract `create_chat`, `generate`, `make_tool_result_message`, `is_quota_error`. `LLMService` (`service.py:192`) extends `lingtai.kernel.llm.service.LLMService` ABC.
- **Adapter registration** — `_register.py` registers exactly four factories: generic HTTP `openai` and `anthropic`, native OAuth `codex`, and local-CLI `claude-code`. Codex ignores generic API keys but honors an explicit `base_url` and resolves OAuth credentials at its request boundary; Claude Code drops generic HTTP settings because its CLI owns transport, and takes the resolved `api_key` (manifest `api_key_env`, default `CLAUDE_CODE_OAUTH_TOKEN`) as its setup-token credential.
- **Effective endpoint** — `LLMService.effective_base_url` (`service.py:406`) returns the primary adapter's `effective_base_url` (configured `base_url`, else the SDK-resolved official endpoint — `OpenAIAdapter.effective_base_url`, `AnthropicAdapter.effective_base_url`) so credential-reusing capabilities (the default Vision route) never send the key to a guessed host.
- **Interface converters** — imported by adapter session modules (e.g. `openai.adapter` imports `to_openai`, `to_responses_input` from `interface_converters.py:120`).
- **Rate gating** — `LLMAdapter._setup_gate(max_rpm)` creates `APICallGate`; `_wrap_with_gate()` returns `_GatedSession` proxy for sessions.
- **Explicit context history rebuild** — `context.rebuild` reconstructs canonical prompt sources before the summary engine calls the session's `request_history_rebuild()` hook (`src/lingtai/tools/context/__init__.py:204-239`, `src/lingtai/tools/system/summarize.py:259-307`). Claude Code accepts that hook even when there are zero pending summaries, discard only their provider-continuation acceleration state, and make the next request replay full canonical history; ordinary per-turn republication of identical prompt/tool content remains continuation-preserving. The provider bullets below own the exact reset state and focused tests.

## Composition

- **Factory pattern** — `LLMService._adapter_registry` (class-level dict) maps provider name → `Callable[..., LLMAdapter]`. Each factory receives `(model, defaults, **kw)` and lazy-imports the adapter module. HTTP-capable factories forward `default_headers` to SDK-backed adapters; `claude-code` deliberately drops them because the local CLI owns its own HTTP stack.
- **HTTP identity headers** — `identity_headers.py:12-53` builds `X-LingTai-Client`, optional `X-LingTai-Version`, and optional `User-Agent: LingTai/<version>`, then merges them under caller headers case-insensitively. The OpenAI-compatible and Anthropic-compatible adapters consume this helper at SDK construction time. There is no per-provider header policy (`LLMService._default_headers_for` forwards only caller `default_headers`).
- **Adapter caching** — `LLMService._adapters` keyed by `(provider, base_url)` tuple (`service.py:254`). Double-checked locking via `_adapter_lock` (`service.py:255`).
- **Session tracking** — `LLMService._sessions` dict maps `st_<12-hex>` session IDs to `ChatSession` instances (`service.py:257`). Untracked sessions get `session_id=""`.
- **Gated sessions** — `_GatedSession` (`base.py:19`) proxies `send()` and `send_stream()` through `APICallGate.submit()`. The proxy is transparent in *both* directions: attribute writes forward to the inner session via `__setattr__` (`base.py:45-48`, keeping only the proxy's own `_inner`/`_gate` slots via `_PROXY_SLOTS`, `base.py:37`) and reads fall through via `__getattr__`. Write-forwarding is load-bearing: `LLMService.create_session`'s `session_id`/`_agent_type`/`_tracked` writes must reach the inner session or `ChatSession.get_state()` would report identity-less, wrongly-tracked state for every gated session, and every adapter's `send()`/`send_stream()` fires `self.pre_request_hook(...)` on the inner session. The named `pre_request_hook` property (`base.py:62-74`) is belt-and-braces — its setter stores the hook on `self._inner`, the same place `__setattr__` would put it — so the object whose `send()` reads `self.pre_request_hook` before the API call always holds it and the kernel drain hook fires under rate gating. The proxy never invokes the hook itself; the inner adapter continues to own request invocation/timing.
- **Codex factory** — `_register.py:_codex` builds one `CodexOpenAIAdapter` with deferred OAuth binding to exactly one account: `FixedAccountSource(codex_auth_path or <tui_dir>/codex-auth.json)`. It is registered only as `codex`; the removed `codex-pool`/`codex_pool` spellings fail init validation with a pointer to the external subs-pool proxy (`src/lingtai/intrinsic_skills/system-manual/reference/subs-pool/SKILL.md`). It honors the common endpoint, cache-affinity, compaction, and `service_tier` settings and never logs plaintext paths or credentials.

- **Codex endpoint pool (molt-boundary shuffle)** — an OPTIONAL Codex-only `codex_base_urls` provider-default (list/tuple or comma/newline string; blank entries dropped) lets the `CodexOpenAIAdapter` pick one of several endpoints. Empty/one-valid-entry collapse to the single-`base_url` path above; 2+ entries are chosen at *request time* in the adapter's `create_chat` override (`openai/adapter.py`) as `pool[(stable_agent_offset + molt_count) % len]`. The offset is `sha256(agent_anchor)` (different agents distribute); `molt_count` is read fresh from `<working_dir>/.agent.json` (host/test callers may pass a direct `codex_molt_count` provider-default override); that file is the sibling of the `codex_session_anchor` `init.json` path, and missing/invalid values fall back to 0. Selection is computed at request time because the molt path (`src/lingtai/tools/context/_molt.py`) does NOT rebuild the adapter — so a live process observes molt-boundary changes without a refresh. The endpoint is stable within a molt segment and rotates only at a molt boundary (minimal side effects: a molt already wipes the wire session). On a switch, `create_chat` re-points `self._client` from `_client_kwargs`, dropping the old client and any websocket / `previous_response_id` continuation state it owned so it never crosses endpoints. Endpoint choice never perturbs the request-shape identity, but the identity itself is molt-aware: the generated `session_id`/`thread_id`/default `prompt_cache_key` comes from `codex_session_anchor + current molt_count`, stays stable within a molt, and intentionally changes at a molt boundary. Helpers: `_parse_codex_base_urls`, `_read_molt_count`. Tests: `tests/test_codex_endpoint_pool.py`.

- **Native Codex account lifecycle** — `CodexOpenAIAdapter._select_codex_account` binds the one configured account per context epoch and owns token refresh, exclusion state, and safe attribution. Each `ChatInterface` gets one `_CodexAccountContext` with its own binding, molt marker, exclusion set, and authenticated client; the cached adapter is only the factory/source owner. `CodexResponsesSession.send_stream` performs the hard/explicit context reset before account binding, so a no-summary 100% forced rebuild gets exactly one fresh draw and the following ordinary request reuses it. Approved summarize/reconstruction boundaries rebind; technical transport/self-heal/turn-count resets do not.
  - **Account/continuation isolation:** when the selected account SHA changes, `_codex_refresh_account_for_request` resets the WebSocket epoch before rebinding (`openai/adapter.py:4264-4272`), closing authenticated transport and previous-response/compaction continuation state so no wire state crosses accounts.
  - **One retry owner:** only the final exception escaping Codex's built-in transport/self-heal paths is reported. Structural `usage_limit_reached` adds the account identity to the context's exclusion set and clears the binding, then re-raises; the next bind raises `NoCandidateError`, which the kernel turn loop treats as terminal for the turn (no AED rebuild/replay). A consumed in-session `token_expired` recovery budget instead produces the shared exact `_lingtai_no_aed_retry` terminal representation and cannot enter AED. Success clears the exclusion set.
  - **Shared replay-terminal representation:** Codex uses kernel `mark_llm_replay_terminal`/`llm_replay_terminal_flags`: every provider-owned exception is wrapped, and only exact `LLMReplayTerminalError` carries trusted flags. Adapter and BaseAgent never read or mutate provider marker storage, and both use the shared render-safe exception description before logging/classification. Secondary account telemetry receives only the wrapper's original exception and fails open without replacing the replay-safe wrapper.
  - **Partial output is terminal:** once visible text or tool output was delivered, the session acquires the shared exact `_lingtai_partial_stream` flag before secondary account telemetry; callback failure cannot replace that wrapper, and the partial flag stays higher priority when merged with no-AED recovery exhaustion, so BaseAgent ends that turn rather than replaying already-visible output.
  - **Safe attribution:** response usage and the token ledger carry only `codex_auth_path_sha8` / `codex_auth_path_source` / `codex_account_id_sha8`. Plaintext token contents never enter metadata, and no account health/cooldown state is persisted. Tests: `tests/test_codex_native_multiaccount.py`, `tests/test_codex_account_source.py`.
  - **`service_tier`** — one normalizer for `codex` and `openai` (`_normalize_service_tier`, `_register.py:43`): `fast` → wire `priority`; `auto`/`default`/`flex`/`priority` verbatim; absent is omitted; any other value raises `ValueError` (and fails `init_schema` validation first). Reaches both Codex REST and WebSocket transports identically because `CodexOpenAIAdapter` stores it once (`_codex_service_tier`) and both transports build their request `kwargs` from the SAME `self._extra_kwargs` (`openai/adapter.py`). The `_openai` factory forwards the same normalized value to `OpenAIAdapter(service_tier=...)`, which adds it to Responses and Chat Completions request kwargs. `anthropic`/`claude-code` never forward it.

- **Claude Code factory** — `_register.py:_claude_code` builds `ClaudeCodeAdapter`, registered only as `claude-code` (the removed `claude_code` spelling fails init validation with a pointer to `claude-code`). It maps the resolved `api_key` to `oauth_token` (a `claude setup-token` token; optional — `init_schema.llm_credential_required` exempts `claude-code`, so a declared-but-unset `api_key_env` reaches the factory as `None` instead of failing boot), drops `base_url`/`default_headers` (the CLI owns transport), passes an empty model as `None` (no `--model`: Claude Code's default model), and passes the runtime-only `claude_code_config_anchor` that `service.py:build_provider_defaults_from_manifest_llm` derives from the agent's resolved `init.json` (never a manifest pass-through key). **Auth order**, resolved per invocation by `_prepare_child`, which delegates to `claude_code/auth.py` (`prepare_claude_child`, `resolve_setup_token`, `choose_private_config_dir`/`ensure_private_dir`, `LocalLoginCache`, `ClaudeCodeError`/`ClaudeCodeAuthError`, re-exported by `adapter.py`) — the same module `tools/daemon` calls for its `claude`/`claude-p`/`claude-code` backends, so there is one policy: (1) *setup-token* — the explicit token, else process env `CLAUDE_CODE_OAUTH_TOKEN` (blank = absent); the child env gets exactly that token as `CLAUDE_CODE_OAUTH_TOKEN` plus `CLAUDE_CONFIG_DIR` = a private 0700 dir (`<tempdir>/lingtai-claude-code/<sha256(anchor)[:16]>`, re-created if the OS temp cleaner removed it; anchorless adapters use a `mkdtemp` dir removed by `weakref.finalize`; its `.claude.json` is pre-seeded by `auth.seed_private_config` with `hasCompletedOnboarding` — plus trust for the daemon interactive bridge's own managed worktree — merging only missing keys, atomically and 0600), replacing any inherited value, and argv `--setting-sources user` (only that empty private dir's settings; keeps Claude Code's transcript retention cleanup); (2) *local login* — no token and `preset_connectivity.claude_cli_login_status` (`claude auth status --json`, a local status read) reports `loggedIn: true` (or is inconclusive): the inherited config dir is kept (on macOS the login lives in the Keychain entry tied to it) and argv `--setting-sources ""` drops user/project/local settings files, so `~/.claude` hooks, settings, and CLAUDE.md memory are not loaded (managed policy settings, `~/.claude.json` state, and the credential store still are); a logged-in/inconclusive verdict is cached per adapter, "not logged in" is re-checked next request; (3) *neither* — `ClaudeCodeAuthError` wrapped by `_terminal_auth_error` in the kernel's exact no-AED-retry marker (`mark_llm_replay_terminal`), so `BaseAgent` goes ASLEEP with the guidance instead of burning AED attempts. Every mode strips `preset_connectivity.CLAUDE_CODE_STRIPPED_ENV` — `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` (API-key billing), `ANTHROPIC_BASE_URL` (would send the token elsewhere), and the `CLAUDE_CODE_USE_{BEDROCK,VERTEX,FOUNDRY,ANTHROPIC_AWS,ANTHROPIC_GOOGLE_CLOUD,MANTLE,GATEWAY}` provider switches — plus any inherited `CLAUDE_CODE_OAUTH_TOKEN`; proxy variables pass through; the adapter's `strip_env` only adds names. CLI-reported auth failures (a missing binary, not-logged-in stderr, or an `is_error` envelope with an auth marker or `api_error_status` 401/403) take the same terminal path with mode-specific guidance; other CLI errors stay ordinary retryable `ClaudeCodeError`s. The adapter drives `claude -p --output-format json`: the canonical `ChatInterface` remains LingTai's source of truth, while the first successful CLI result provides a remote `session_id` used by later `--resume` calls. A resumed call serialises only canonical entries committed since the preceding successful response, so remote history is not duplicated; missing/failed/overflowed remote state is cleared and the next call rebuilds from full canonical history. `update_system_prompt` / `update_tools` clear that continuation **only when the content actually changes** (`_resync_stable_context` compares a sha256 over system prompt + tool schemas): `SessionManager.send` rebuilds both on *every* turn, so an unconditional reset there would clear the session ID before each call and `--resume` would never be sent. An explicit `request_history_rebuild()` clears the remote session ID and canonical-entry cursor, so the next request omits `--resume` and serialises canonical history from entry zero (`claude_code/adapter.py:334-337`, `claude_code/adapter.py:505-511`); focused resumed-summary, zero-pending, and cold-session regressions live in `tests/test_claude_code_adapter.py:571-658`. The CLI emits a single JSON action (`tool_call`/`tool_calls`/`final`) which is parsed back into an `LLMResponse`; LingTai's own loop executes the tools. Built-in CLI tools are disabled (`--tools ""`), ambient MCP is isolated (`--strict-mcp-config` + empty `--mcp-config`), and the default `system_prompt_mode="replace"` passes `--system-prompt-file` so Claude Code's native system prompt is replaced by LingTai's, in both auth modes. `ClaudeCodeChatSession.send` snapshots the canonical history before mutating it and restores that snapshot if the hook / tool pairing / CLI call / parsing raises, so a failed turn never strands the just-added user / tool-result message; on *successful* context-overflow recovery (`rounds > 0`) it injects a `[kernel]` overflow notice via `_inject_overflow_notice` before recording the assistant turn (same idiom as `openai`/`anthropic`). For health checks it is the one *CLI-backed provider* (`lingtai.kernel.preset_connectivity._CLI_BACKED_PROVIDERS`): gauged by module importability plus the same auth order (a setup-token in the preset's `api_key_env` or `CLAUDE_CODE_OAUTH_TOKEN`, else `claude auth status`), never a TCP probe or model request. See `claude_code/adapter.py`. The provider-local `live_effort.py` descriptor publishes the installed CLI vocabulary, exact model/CLI route fingerprint (an omitted model is the `cli-default` route, `CLAUDE_CLI_DEFAULT_MODEL_ROUTE`), and construction baseline to the neutral kernel port; omitted/`default` thinking sends no `--effort` (`agent.py:_OMITTED_THINKING_DEFAULT_SENTINEL_PROVIDERS` includes `claude-code`); `ClaudeCodeChatSession` snapshots that decision once per logical dispatch, reuses it for retries, and records safe emitted/omitted effort evidence in usage metadata.

## State

Tool-result metadata is stored canonically on `ToolResultBlock.metadata` and
projected by the Anthropic, OpenAI Chat Completions, and OpenAI Responses
converters. Dictionary and string results use the same projected `_meta` roots;
canonical history retains the sidecar separately and replay does not strip old
agent snapshots. No provider converter implies inbound recovery unless that
provider has a matching converter.

Provider converters project the canonical `ToolResultBlock.metadata` sidecar
into one model-visible `_meta` envelope. This projection is deliberately
handler-agnostic: dictionary results merge the envelope and string/non-dict
results use a structured `{result, _meta}` output. Canonical history stores the
sidecar separately so replay/deserialization preserves it without rewriting
historical holders.

- **Class-level** — `LLMService._adapter_registry` (shared across all instances); `LLMAdapter._gate` (per-adapter instance).
- **Instance-level** — `LLMService._adapters` cache; `LLMService._sessions` registry; `APICallGate._timestamps` deque for RPM window.
- **Provider defaults** — `LLMService._provider_defaults` dict injected at construction (`service.py:245`). Drives model, base_url, max_rpm, `default_headers` (caller headers preserved under the shared LingTai identity defaults), the Codex per-agent identity (`codex_session_anchor`/`codex_thread_salt`), Codex token-file selection (`codex_auth_path`), the optional Codex endpoint pool (`codex_base_urls`; direct host/test defaults may also pass `codex_molt_count`), the `openai` `wire_api` selector (`chat_completions` default / `responses`; legacy `auto` = `chat_completions`), the common `service_tier` selector (`openai` and `codex`), the generic `openai` knobs (`inject_reasoning_fallback` / `prompt_cache_namespace`), and the runtime-only `claude_code_config_anchor` (the agent's resolved `init.json`, injected for `claude-code` when `working_dir` is known and never read from the manifest). Build it from `manifest.llm` via `build_provider_defaults_from_manifest_llm()` (`service.py:129`) — the opt-in `_PROVIDER_DEFAULTS_PASS_THROUGH_KEYS` safelist (`service.py:94`) ensures adapter-consulted manifest fields propagate, skipping `None` values. The retired `api_compat` / `reasoning_effort_vocab` / `use_responses_api` keys are recognized-and-ignored by `init_schema` and never reach an adapter. No adapter sends the generic OpenAI Responses `context_management` auto-compaction field; Codex uses standalone `/responses/compact` instead. `cli.py:_load_init`, `agent.py:_setup_from_init`, and the daemon's preset path (`tools/daemon/__init__.py` `_llm_defaults_from_manifest`) all use this helper to stay in sync.
- **Key resolution** — `LLMService._key_resolver` callable (`service.py:244`); defaults to `os.environ.get(f"{PROVIDER}_API_KEY")`.

## Notes

- **Wire tool descriptions are single-sourced** — every provider payload builder for registered `FunctionSchema` tools resolves its top-level tool description through the kernel helper `wire_tool_description` (`src/lingtai/kernel/llm/base.py:190`) rather than hardcoding either string. It returns the `WIRE_TOOL_DESCRIPTION` pointer constant only while the resident `## tools` section is opted in via `LINGTAI_TOOL_PROSE_SECTION_ENABLED`; by default that section is not rendered and the helper returns the full `FunctionSchema.description` so the prose still reaches the model exactly once. Call sites: openai `_build_tools` (`openai/adapter.py:1149`) / `_build_responses_tools` (`openai/adapter.py:1266`), anthropic `_build_tools` (`anthropic/adapter.py:112`). The full prose stays in canonical `ChatInterface` tool snapshots (`FunctionSchema.list_to_dicts` at the `add_system` call sites) in both states, and additionally in the system prompt's `## tools` section when that section is opted in; nested parameter descriptions are untouched. Structured-output pseudo-tools keep their task-specific descriptions. `claude_code` is excluded from the helper — it has no tools wire array; `_render_system_context` serialises the full description into its `# AVAILABLE TOOLS` block, which *is* its system-prompt side. That block sits directly beside `# AGENT SYSTEM INSTRUCTIONS` in one cached system file, so while the `## tools` section was unconditional this adapter shipped two byte-identical copies of every tool's prose per turn — the concrete waste the default-off gate removes. Tests: `tests/test_wire_tool_description.py`, `tests/test_tool_prose_section_gate.py`.
- **Anthropic compatibility** — any Anthropic-compatible (Messages API) endpoint is reached through the `anthropic` provider plus `base_url` (`src/lingtai/llm/anthropic/adapter.py:699-740`); the former `custom` + `api_compat: "anthropic"` route was removed with the four-family collapse.
- **Abstract methods** — `LLMAdapter` requires: `create_chat()` (`base.py:157`), `generate()` (`base.py:192`), `make_tool_result_message()` (`base.py:209`), `is_quota_error()` (`base.py:221`).
- **Tool-call ID dual system** — Provider-issued wire IDs (e.g. Anthropic `tool_use_id`, OpenAI `tool_call_id`) flow through `tool_call_id` kwarg. LingTai issues its own `_tool_call_id` (`service.py:35`: `tc_<unix>_<4-hex>`) stamped onto every result dict for agent-level correlation.
- **Interface converters** — three wire families:
  - `to_anthropic`/`from_anthropic` — Anthropic Messages format (system excluded, ThinkingBlock with signature round-trip)
  - `to_openai` — Chat Completions format (tool results as `role=tool`, ThinkingBlocks emit as `reasoning_content` for thinking-mode OpenAI-compatible endpoints' round-trip; endpoints that don't know the field ignore it). One-way only — OpenAI history rehydration goes through `content_block_from_dict` on the canonical interface, not a reverse converter.
  - `to_responses_input` — Responses API input items (`function_call` / `function_call_output` shapes; non-empty ThinkingBlocks replay as `reasoning` items with `summary_text`, before assistant text/calls; `interface_converters.py:532`).
